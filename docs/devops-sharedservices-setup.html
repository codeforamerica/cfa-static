Putting the CfA Static site on SharedServices

One-time setup for the internal deployment of codeforamerica/cfa-static. The site (unchanged) also keeps deploying publicly to GitHub Pages — both build from the same commit and only differ in the URL they are stamped with. Everything for the internal side already lives in the repo; what's left is platform registration and configuration, in this order. Each step explains what's going on in plain terms and links where you need to go.

What's already in place (nothing to do here)

  • sharedservices-deploy.yaml — the deploy workflow. Builds the site with the internal URL settings, uploads the result to the platform's S3 bucket, and flushes the edge cache. Runs manually (Actions → Deploy to SharedServices), not on every push, while this is being piloted.
  • app.yaml — the platform registration file declaring this a static app whose build output is _site.
  • A README section summarising all of this, and this walkthrough.

Step 1 — Register the app in the platform Platform DevOps

SharedServices doesn't know this site exists yet. The platform's rule is that everything it hosts is declared in one central infrastructure repo — shared-services-infra (likely requires a DevOps login to view). A declaration is a small YAML file called a static app spec: add a cfa-static spec to tofu/configs/static-app/specs/ (open a PR there), then apply it with tofu apply — the tool that reads the declaration and creates the real AWS resources.

Values for the spec (mirroring the repo's app.yaml):

FieldValueNote
namecfa-staticMatches the GitHub repo
name_shortcfa-static10 chars — within the 12-char limit
typestaticNo server — Okta gates it at the edge
descriptionCfA Static site template — self-documenting reference deploymentFree text

Worth a comment in the PR: this repo intentionally doesn't follow the sharedservices-* naming convention, because it's the template's own canonical repo rather than an app scaffolded from the platform template.

Ask DevOps to hand back four values from the apply — the next steps need them exactly:

  • the deploy role ARN (the layer's deploy_role_arn output) — what lets GitHub upload to this app's corner of the bucket
  • the bucket name of the shared static-hosting bucket
  • the CloudFront distribution ID of the shared distribution
  • the app's endpoint URL (the layer's endpoint_url output) — https://cfa-static.apps.dev.services.cfa.codes in the development environment
What applying actually does: provisions a per-app deploy role and grants that role permission to write to the shared static bucket under this app's prefix and to invalidate the shared CloudFront distribution. Nothing else — the app is static, so there's no container, no database, no network config to make. The app is served at the root of its own subdomain; a CloudFront edge function maps that subdomain to the app's prefix in the bucket behind the scenes, so the site itself never needs a path prefix.

Step 2 — Configure the GitHub environment Repo admin

The deploy workflow reads its settings from a GitHub environment — a named bag of variables and secrets attached to the repo, so none of it lives in the code. Create one called development: Settings → Environments → New environment (if you can't see that screen, hand this step to whoever granted your repo access — it's admin-only).

Add these environment variables (exact names — the workflow looks these up):

NameValueWhat it's for
AWS_REGION us-east-1 Where the bucket lives
STATIC_BUCKET bucket name from step 1 Where the files get uploaded
STATIC_PREFIX cfa-static The app's slot in the shared bucket — where the workflow uploads. Must match the app name in the platform spec; the URL is unaffected (each app gets its own subdomain)
SITE_URL the app's endpoint URL, e.g. https://cfa-static.apps.dev.services.cfa.codes The address the site stamps into its canonical URLs, sitemap, and social cards. Get the real value from DevOps after step 1 — it's the static-app layer's endpoint_url output: one subdomain per app, no path appended. No trailing slash — the build validates this and fails loudly rather than publishing odd URLs

And these secrets:

NameValueWhat it's for
CLOUDFRONT_DISTRIBUTION_ID distribution ID from step 1 Flushed after each deploy so changes show immediately
AWS_ROLE_ARN deploy role ARN from step 1 The AWS identity the workflow borrows during a run (kept as a secret to match the platform convention)
The site-deployment workflow needs no stored AWS access keys. When the workflow runs, GitHub and AWS exchange short-lived tokens: GitHub says "I'm this repo's deploy job", AWS checks that a role trusts exactly that repo, and hands out credentials that die when the run ends. That's OIDC — and it's why the deploy can be triggered by anyone with write access without them ever holding an AWS credential.

Step 3 — Run the first deploy You

Go to the workflow's page — Actions → Deploy to SharedServices — pick main, and hit Run workflow.

What the run does, in order:

  1. Check configuration. Fails immediately, naming any missing variable — intentional, so a typo in step 2 surfaces as "MISSING: STATIC_BUCKET" rather than a deploy to the wrong place
  2. Build. Same npm ci + npm run build as the public Pages deploy, from the same commit — differing only in the internal SITE_URL. No path prefix applies, because the app is served at the root of its own subdomain
  3. Upload the build. The exact files deployed get attached to the run as an artifact ("sharedservices-site") — download it from the run's page if you ever need to inspect what went out
  4. Sync to S3 into s3://<bucket>/cfa-static/. --delete means files removed from the site also disappear from the bucket — no stale pages left behind
  5. Invalidate CloudFront so the new content is live immediately

Step 4 — Verify You

Ask DevOps for the live URL from step 1 — the app's own subdomain, e.g. https://cfa-static.apps.dev.services.cfa.codes. Then:

  • Visit the URL in a private/incognito window — you should hit the Okta sign-in, before any part of the site loads. That's the edge doing access control; the site itself never sees auth
  • Sign in, land on the homepage, and click into a deep page — links should keep working at the subdomain root
  • Try the search box on the search page — results should come from the internal copy, not the public site
  • Spot-check the footer/social links and the feed at /feed.xml on the subdomain — URLs inside them should point at the internal origin
  • While logged in, view source on the homepage and confirm rel="canonical" points at the internal URL

After the pilot

Two deliberate restrictions that can be lifted once this has proven itself, both one-line changes:

  • Deploys are manual. Adding an on: push trigger makes every merge to main publish internally too, matching the platform's other static apps
  • Deploy logic lives in this repo. The platform offers a shared workflow for static apps; extending it to accept a pre-built artifact lets this repo (and future sites from the template) call it instead of running AWS commands directly — worth a follow-up issue

Questions at any point: #eng-team — the platform team who own the infra in step 1. Background on how SharedServices treats static apps is in the platform's own contract, AGENTS/static.md.
